# КТ1 · Архитектурное ревью: самопроверка проекта (трек ML-инжиниринг)

Сопоставление требований рабочей программы (раздел 9, рубрикатор) с реализацией, известные ограничения
и ответы на вероятные вопросы ревьюеров. Ревью — 21.11 и 28.11.

## 1. Техническая реализация (40 %)

| Требование РПД | Где реализовано | Как проверено |
|---|---|---|
| Интерактивное веб-приложение на Taipy | `app/main.py`: три страницы с навигацией — «Обзор потока», «Модель-советчик», «Объяснения (XAI)» | Ручной прогон в браузере (Playwright), ошибок в консоли и журнале нет |
| Корректная передача состояния (State) | Фильтры, порог, выбранная карточка — переменные State; пересчет в `on_filter`, `_apply_threshold`; пакетные обновления через `with state as s` | Два клиента одновременно: порог одного не меняет KPI другого |
| Интеграция предобученной модели (.joblib) | `advisor.load_model()` — загрузка один раз при старте; путь переопределяется `IAVD_MODEL` | Метрики в UI совпадают с метаданными обучения (P 42,3 %, R 90,0 %) |
| Асинхронный инференс, отсутствие блокировок UI | `on_run` → `invoke_long_callback(_run_inference)` → `on_status` (прогресс каждые 0,5 с); PDP — тоже в фоне | Во время инференса двух клиентов третий пользуется обзором без задержек; 90 792 карточки за ~2 с |
| Визуализация XAI: SHAP | Waterfall по клику на карточку очереди; глобальная важность и вклад значений по предрасчитанным SHAP (`model/advisor_baseline_shap.npz`) | Аддитивность: база + вклады = оценка модели (расхождение < 1e-14) |
| Визуализация XAI: PDP | Вкладка XAI: PDP + ICE по 1 000 карточкам, сетка 5–95 %, распределение признака под графиком | Пересчет по выбору признака 0,1–0,8 с в фоне |

## 2. Аналитическая обоснованность (30 %)

- Положительный класс — реальный инцидент (16,1 % размеченных карточек); «Не указан» и «Дубликат» без эталона
  исключены (СРС к 3.2).
- Главные метрики — полнота (FN непростителен), затем точность (нагрузка аналитиков). Порог 0,37 — максимальный
  при полноте ≥ 90 %; в очереди без вердикта он отправляет к разбору 22 % карточек.
- Признаки — только известные при создании карточки; поля процесса разбора исключены (утечка таргета).
- Дрейф: при проверке по времени ROC-AUC падает с 0,92 до 0,79, доля инцидентов по месяцам 3–28 %.
  Предупреждение выводится в интерфейсе.
- Сверка с контрольными числами банка EDA (240 295 карточек, FP 62,7 %, L2: 3 312 и FP 31,9 %, пик 8:00 UTC).

## 3. Информационный дизайн (30 %)

- Одна серая палитра; красный — только сигнал «требует реакции» (FP-нагрузка, критичность, к разбору, FN),
  синий — выделение (тренд, пиковый час, рабочая точка, вклад к FP).
- Data-ink ratio: подписи значений вместо осей у столбчатых, без легенд и рамок, сетка только где нужна оценка уровня.
- Иерархия экрана: F-паттерн — фильтры и управление слева, KPI сверху, графики, затем таблица.
- Тип графика по задаче: динамика — столбцы + скользящее среднее; структура — горизонтальные столбцы по убыванию;
  качество модели — матрица ошибок и PR-кривая (дисбаланс классов); объяснение — waterfall, PDP + ICE.
- Заголовки графиков формулируют вывод или динамический показатель (например, доля FP под фильтром).

## 4. Известные ограничения (честно сказать на ревью)

1. **Модель — своя базовая**, т. к. модели курса нет в материалах; модель курса подключается через `IAVD_MODEL`,
   но при другом наборе признаков потребуется правка `build_features`.
2. **Версии пакетов** не сверены с `pyproject.toml` курса (scikit-learn 1.9.1, Taipy 4.1.1).
3. **Дрейф**: модель оценена на случайном разбиении; на новом потоке качество ниже (ROC-AUC 0,79).
4. **Категории кодируются порядковыми номерами** (без нативных категориальных сплитов) — ради точного SHAP;
   качество от этого не упало.
5. **PDP при коррелированных признаках** (`Наименование` ↔ `categoryMain` ↔ `Источник инцидента`) может приписывать
   эффект не тому признаку; ICE и распределение под графиком показаны, чтобы это было видно.
6. **Полный датасет в памяти процесса** (загружается один раз, общий для клиентов); State хранит только срезы клиента.
7. Автотестов нет; проверка — ручные сценарии в браузере.

## 5. Вероятные вопросы и короткие ответы

- *Зачем асинхронный инференс, если он идет 2 с?* — Модель курса до 12 ГБ и медленнее; синхронный callback
  занял бы обработчик клиента, и UI перестал бы реагировать. `invoke_long_callback` выносит работу в поток,
  State в нем не используется — прогресс передается через словарь по `state_id`.
- *Почему State не хранит весь датасет?* — Переменные State копируются на каждого клиента; общий read-only
  датасет живет на уровне модуля, в State — только производные (срезы, фигуры, KPI).
- *Почему порог 0,37, а не 0,5?* — Порог выбран из цены ошибок: пропуск дороже ложной тревоги, поэтому фиксируем
  полноту ≥ 90 % и максимизируем точность.
- *Чем SHAP отличается от PDP?* — SHAP — локальный вклад признака в оценку конкретной карточки (сумма вкладов
  = оценка); PDP — глобальная средняя зависимость оценки от признака при подстановке значения всем карточкам.
- *Почему ROC-AUC не главная метрика?* — При 16 % инцидентов ROC не показывает цену FP; PR-кривая показывает.
